# Contract: The verification matrix

**Feature**: `005-design-system-foundations` | **Date**: 2026-09-05

What the suite captures, when it runs, and what fails a change. The conformance gate currently
claims coverage it does not have; this contract is what makes the claim true.

## The matrix

| Axis  | Values                | Count |
| ----- | --------------------- | ----- |
| story | every published story | 299   |
| theme | light, dark           | 2     |
| width | 375, 768, 1280        | 3     |

**1,794 captures**, from 279 baselines today. States are already separate stories, so the state axis
rides on the story axis rather than being duplicated.

**The two sets do not currently agree.** 25 stories have no baseline — `Tooltip`'s thirteen were
never committed at all — and 3 baselines name stories that no longer exist. Phase 1 reconciles them
at the existing axes *before* expanding, because multiplying an unreconciled set by six multiplies
the discrepancy, and a set-equality check then keeps them reconciled as its own step in the `visual` job,
ahead of the diff-scoped run, where diff scoping cannot outrun it (the `web` job never builds the
Storybook index it reads).

| Run          | Story selection              | Axes            |
| ------------ | ---------------------------- | --------------- |
| Pull request | the stories the diff affects | the full matrix |
| Nightly      | every story                  | the full matrix |

**Scoping is by story, never by axis.** A narrower pull-request run may not be introduced without
amending FR-061, so that "verified" has one meaning. The prohibition is enforced where it can be
broken: `scripts/visual/run.mjs` emits the complete axis set for every story it selects and exposes
no flag that removes one.

This does not weaken constitution VII. The *selection* is still the affected stories — CI stays a
court — and each selected story is now captured across the axes the review protocol always claimed.

## Mechanism

Already proven in this repository, so nothing is invented.

- **Theme**: `/iframe.html?id=<id>&viewMode=story&globals=theme:<light|dark>`, which the preview
  decorator turns into `document.documentElement.dataset.theme`. This is exactly what
  `tests/visual/focus-ring.spec.ts` already does.
- **Width**: the viewport, set before navigation, as the retiring `visual-mobile` path already does
  at 375.
- **Settle**: unchanged. The suite waits for Storybook's own render phase to reach `completed`,
  `finished` or `errored`, which is what makes a first capture of a story with an interaction
  deterministic. This logic is load-bearing and is not touched.

`visual-mobile` is retired — every story is captured at every width now, so a per-story tag saying
"also capture this one narrow" has nothing left to say. `visual-full-page` **stays**: it names a
property of the subject, not an axis.

## Baseline generation

Baselines are regenerated by a manually dispatched workflow on `ubuntu-latest`, never on a
developer's machine.

The repository has already paid for the alternative: a full-page baseline captured locally differs
from CI's renderer by around 2% of pixels, which is why the application-route suite carries its own
looser diff ratio and a comment explaining it. This feature regenerates baselines three times; by
hand, that is three chances to commit a subtly wrong generation.

**Storage.** 279 baselines occupy 18 MB. The matrix is not six times that: git stores one blob per
distinct content, and most stories are width-invariant, so a story's three widths are three paths
onto one blob. Only the theme axis is guaranteed to differ. Steady state is around 35-40 MB; what
accumulates is history, roughly 150 MB across the feature's three global repaints.

## What else fails a change

The screenshot is not the only gate, and for the three phases that repaint everything it is not a
useful one — a diff carries no information when every pixel is expected to move. These are what
carry those phases.

| Check                                   | Fails when                                                                             |
| --------------------------------------- | -------------------------------------------------------------------------------------- |
| `packages/design-system/tokens/build-tokens.test.mjs`          | a colour edit drops a measured pair below its floor, or a theme's key set diverges     |
| `scripts/checks/token-scale.mjs`        | an arbitrary value, a raw literal or a hand-written `var(--ds-*)` reaches a component  |
| `scripts/checks/tier-deps.mjs`          | a primitive imports a composite, or anything in the package imports from `apps/`       |
| the axe scan, inside the story loop     | a story has an accessibility violation not in the dated allowlist                      |
| the spec completeness check             | a component spec leaves a state in the closed vocabulary unanswered                    |
| the story/baseline set-equality check   | a story has no baseline, or a baseline names no story                                  |
| the landmark check                      | a route renders anything other than exactly one main landmark                          |
| `tsc -b`                                | a shared type drifts between the design system and the application                     |

`tsc -b` is listed because the application's own unit runner is transpile-only: it is the only thing
in the workspace that catches a type drift across the two packages.

## Accessibility: the allowlist, and why it is a debt

`@storybook/addon-a11y` is installed and inert — nothing runs it outside the Storybook UI. The scan
moves into the Playwright story loop, at the point the screenshot is taken, reusing the scoping, the
theme mechanism and the settle logic that are already correct there.

The finding volume across 32 existing components is unknown until it first runs, which is the spec's
Risk 8. `scripts/visual/a11y-allowlist.json` absorbs it: one entry per accepted finding, carrying
the component, the rule, the date and the fix owed. An entry is a named debt, not a suppression. The
file is empty by the end of the retrofit phase, and a check fails if an entry outlives the feature.

## The focus ring

Focus states are invisible to a static screenshot — a story never renders a focused control, which
is exactly why the ring shipped broken in both themes and was caught only by an interaction test.
That test is extended from five controls to every focusable primitive, in both themes, and stays an
interaction test. No amount of baseline coverage replaces it.
