# Tasks: Design System Foundations

**Input**: Design documents from `/specs/005-design-system-foundations/`

**Prerequisites**: [plan.md](./plan.md), [spec.md](./spec.md), [research.md](./research.md),
[data-model.md](./data-model.md), [contracts/](./contracts/), [quickstart.md](./quickstart.md)

**Tests**: Included and mandatory. The nine scenarios in [quickstart.md](./quickstart.md) are the
source, and every verification task names the scenario it encodes. This feature is almost entirely
TypeScript, Node and Playwright, where there is no `xfail` marker: a test is written and left
failing, and the implementing task is what turns it green, so a test task and its implementer are
never separately committed. Where that applies it is stated on the task rather than left for the
committer to infer.

**Organization**: grouped by the six phases [plan.md](./plan.md) fixes, not by user story priority,
and the difference is deliberate. Three phases repaint every pixel — the palette and the typefaces,
the structural tier's rhythm, the retrofit — and a visual diff carries no information when
everything is expected to change. The phase order is chosen so that the repaint happens as few times
as possible and so that the one phase which changes the harness changes no value. Story labels are
carried per task; a phase serving two stories says so.

## Format: `[ID] [P?] [Story] Description`

- **[P]**: can run in parallel — different files, no dependency on an incomplete task
- **[Story]**: US1..US7, mapping to the user stories in [spec.md](./spec.md)
- Every task names its exact file path

## Path Conventions

Per [plan.md](./plan.md): `packages/design-system/{tokens,specs,src,.storybook,__screenshots__}/`,
`apps/web/`, `tests/visual/`, `scripts/{checks,visual}/`, `.github/workflows/`, `CLAUDE.md`.

## Numbering starts at T501, deliberately

001 reaches T110, 002 runs T201 to T215, 003 runs T301 to T412 and 004 runs T401 to T458. Ids
resolve **across** features since T202, so they have to be unique repository-wide: `spec_lint.py`'s
`task-refs` check treats an id as defined the moment any feature's `tasks.md` says so, and a
colliding range would make "who owed this" unanswerable. A disjoint range costs nothing.

## What every implementer must know before touching a baseline

Baselines are regenerated by the dispatched workflow on Linux, never on a developer machine
(research **D3**). A full-page baseline captured locally differs from the continuous-integration
renderer by around 2% of pixels, which is why `tests/visual/app-routes.spec.ts` already carries its
own looser diff ratio and a comment explaining it. This feature regenerates three times; by hand
that is three chances to commit a subtly wrong generation. Every regeneration task below names its
cause, and the cause goes in the commit body, because a regeneration with no stated cause is
thousands of files nobody can review.

## Phase 3: Theme reachability (plan phase 3 — US3)

**Purpose**: small, application-only, and it is what makes the dark half of phase 2's work
observable by a person rather than only by a test. An entire theme — specified, tokenised,
contrast-measured — currently reaches no reader.

**Independent test**: quickstart scenario 6, all four cases, manually. A flash of the wrong theme is
a first-paint event no still image captures.

**Story goal (US3)**: the reader gets the theme they need, and it is remembered.

- [ ] T533 [US3] Add the theme-resolution script to `apps/web/index.html`: inline, synchronous, **before the stylesheet**, under 500 bytes, reading the stored override and then the system colour-scheme preference and setting the theme attribute on the document element (FR-015, FR-016). Nothing that runs after React mounts can satisfy the no-flash requirement, which is why a few lines outside the component tree are the correct answer in this one place. It is also the one place theme selection can fail closed: browser storage throws outright when a browser is configured to block site data, so both reads are wrapped and fall through to the system preference and then to **light** as the defined default. It is static markup, identical under Vite, on Vercel and on any static server, with no server rendering assumed (constitution XII, research **D11**)
- [ ] T534 [US3] Add `packages/design-system/src/theme/` with a `ThemeProvider` and a `useTheme` hook owning the stored override and the media-query subscription, so that a system change is honoured live for a reader who has not overridden (FR-014). The override is a preference in the reader's own browser: never transmitted, never joined to a profile, readable by nobody but the reader. ## Dependencies & Execution Order

### Phase dependencies

The six phases are strictly ordered and the ordering is the plan's central engineering decision, not
a preference. Each is independently green and separately mergeable.

- **Phase 1** depends on nothing. It must come first because it is the only phase in which the
  harness change can be proved correct by identity (T505), and that proof expires the moment any
  value moves.
- **Phase 2** depends on phase 1 for the matrix that will carry it, since its own diff is
  uninformative.
- **Phase 3** depends on phase 2 for a dark palette worth reaching. It sits before phase 4
  deliberately: small, application-only, and what makes phase 2's dark half observable by a person.
- **Phase 4** depends on phase 2's tokens. Its primitives cannot be built against values that do not
  exist.
- **Phase 5** depends on phase 4 absolutely — its targets do not exist until the primitives do.
- **Phase 6** depends on phases 4 and 5 for something to document and to govern.

### User story dependencies

- **US5** (phase 1) depends on nothing and unblocks the verification of everything after it.
- **US1** (phase 2) is the precondition the spec names: no amount of review discipline fixes a
  component that has nothing to reach for. It unblocks US2 and US4.
- **US4** (phase 2, completed in phase 5) needs US1's typography roles.
- **US3** (phase 3) needs US1's palette; nothing needs US3.
- **US2** (phases 4 and 5) needs US1's tokens and is the only story that removes an existing defect
  from the live product.
- **US6** and **US7** (phase 6) need US2 finished.

### Within each phase

- A check and the change that makes it pass are one commit wherever the check would otherwise land
  red: T527 with T528, T553 with T551/T552/T554, T571 with T570. Each says so on the task.
- A baseline regeneration is the last task of its phase, never the first — it is the record of what
  the phase did, and dispatching it early records a state nobody intended.
- `product-designer` deliverables (T521, T523, T539) precede every implementer that consumes them.

### Parallel opportunities

- **Phase 2**: T513 through T520 are eight separate token files and run together, after T512 has
  given the generator somewhere to emit them.
- **Phase 4**: T544 through T548 are five separate primitive directories and run together, after
  T543 establishes `Page` and the rhythm it owns.
- **Phase 5**: T554 and T555 touch disjoint container files and run together.
- **Phase 6**: T564, T566 and T567 touch disjoint story files and run together.

Everything else is sequential. A parallel batch is one commit — agents sharing a working tree
interleave in the same files, and splitting that afterwards invents commits that never existed as a
working state.

## Implementation Strategy

`/speckit-implement` is run **one phase at a time**, naming the task range and the stop condition.
Its own completion criteria otherwise push it through every phase in one context, which is how the
judgement in this file gets flattened.

### The MVP is phase 1, and it is not the P1 stories

Ordinarily the MVP is User Story 1. Here it is **phase 1 (T501–T511, US5)**, and the inversion is
deliberate: phase 1 is the only phase whose correctness is provable, it delivers a suite that stops
overstating its coverage, and it is mergeable and valuable on its own even if nothing after it
shipped. A gate that is believed and does not hold is worse than an absent one, because it displaces
the manual check that would otherwise happen.

### Incremental delivery

1. **Phase 1** → the suite captures what it claims. Merge.
2. **Phase 2** → every decision has a token; the palette and the typography are decided. Merge.
3. **Phase 3** → both themes reach a reader. Merge.
4. **Phase 4** → a screen can be assembled. Merge.
5. **Phase 5** → nothing is left on the old foundations, and the landmark defect is gone. Merge.
6. **Phase 6** → the system explains and governs itself. Merge.

Each phase is a reviewable pull request. One pull request carrying all of this would be
unreviewable, which is what the spec's Risk 1 asks for the opposite of.

## Notes

- **[P] means different files, and nothing else.** Two tasks touching one file are sequential no
  matter how unrelated they look.
- **Never commit a red tree**, and run the whole suite rather than the failures an agent mentioned:
  a hand-back names what that agent noticed, and verifying only those inherits its blind spot.
- **The checkbox rides in the same commit as the code that earned it.** A checkbox committed alone
  is a claim with no evidence behind it, and it is the one lie this workflow cannot detect.
- **Principle I holds over this whole feature.** This is a large display feature, and the
  constitution resolves contention over review attention in favour of capture: no phase here may
